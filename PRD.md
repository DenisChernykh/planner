# PRD: «План на месяц»

**Версия:** 1.1  
**Дата:** 11 августа 2026 года  
**Статус:** согласованный продуктовый PRD  
**Часовой пояс продукта:** `Asia/Yekaterinburg`

## 1. Краткое описание

«План на месяц» — закрытый веб-сервис с Telegram-ботом для Участник А и Участник Б. Он заменяет бумажный месячный план: позволяет подготовить и опубликовать план, ежедневно фиксировать выполнение личных и совместных целей, получать только актуальные напоминания и закрывать месяц воспроизводимым отчётом.

Продукт не является универсальным публичным трекером привычек. Первая версия рассчитана на одну пару, один общий календарь и два равноправных аккаунта.

### Главный критерий успеха

Оба пользователя прожили один полный календарный месяц без бумажной версии, каждый достиг не менее 80% успешных применимых личных дней, а система сформировала итоговый отчёт, который можно однозначно воспроизвести из сохранённых записей и снимка опубликованного плана.

## 2. Контекст и проблема

Исходный документ `monthly-plan-template` содержит:

- ежедневные привычки и временные диапазоны;
- количественные цели: вода, шаги, страницы, минуты, подписчики и деньги;
- оценки настроения в несколько моментов дня;
- цели `N` раз в неделю и `N` раз в месяц;
- личные и совместные цели;
- альтернативные способы выполнения по логике «или»;
- ежедневные текстовые задачи и списки действий;
- отдельные итоги Участник Б, Участник А и совместной деятельности.

На бумаге тяжело менять состав следующего месяца, отличать отсутствие данных от невыполнения, рассчитывать частичные недели, исключать уже закрытые цели из напоминаний и строить динамику за несколько месяцев.

## 3. Цели продукта

1. Перенести все смысловые типы записей из исходного плана без сведения их к одному чекбоксу.
2. Сохранить историю прошлых месяцев при изменении будущих планов.
3. Сделать ежедневное заполнение быстрым в вебе и Telegram.
4. Не напоминать о цели, если её применимая норма уже выполнена.
5. Разделять достижение целей и полноту заполнения данных.
6. Давать личную и совместную статистику без двойного зачёта.
7. Подготовить единый продуктовый интерфейс команд для будущего ИИ-ввода.

## 4. Не входит в v1

- публичная регистрация и использование другими парами;
- несколько пространств у одного пользователя;
- автоматический импорт произвольных DOCX;
- нативные приложения iOS и Android;
- интеграции с часами, HealthKit, Google Fit и другими трекерами;
- свободный текстовый парсер на наборе регулярных правил;
- медицинские рекомендации или причинные выводы из корреляций;
- социальная лента, рейтинги и соревнования между пользователями.

## 5. Пользователи, доступ и видимость

### 5.1. Пространство пары

- В продукте существует одно закрытое пространство пары.
- У пространства два равноправных участника: Участник А и Участник Б.
- Оба участника видят весь план, каталог, записи и отчёты.
- Любой участник может редактировать черновик, публиковать план, управлять каталогом и настройками пространства.
- Автор каждого изменения и каждой записи сохраняется в аудите.

### 5.2. Идентификация

- Вход в веб выполняется через Telegram OIDC по Authorization Code flow с PKCE.
- Запрос авторизации защищается параметрами `state` и `nonce` и использует только scopes `openid`, `profile` и `telegram:bot_access`; номер телефона не запрашивается.
- Доступ разрешён только двум заранее внесённым в закрытый allowlist числовым Telegram user ID.
- Устойчивая связь внешней и локальной учётной записи определяется проверенной парой `issuer + subject` и соответствующим числовым Telegram user ID.
- Telegram username не используется как идентификатор и может меняться без потери доступа.
- После успешной OIDC-авторизации создаётся локальная веб-сессия участника; неизвестный или неразрешённый Telegram user ID не получает доступ к пространству.
- Групповые чаты и сообщения от Telegram user ID вне закрытого allowlist игнорируются.
- Все даты, границы периодов и времена уведомлений рассчитываются в `Asia/Yekaterinburg`.

### 5.3. Владение целью

Цель имеет одного из владельцев:

- `memberB` — результат входит только в личный отчёт Участник Б;
- `memberA` — результат входит только в личный отчёт Участник А;
- `shared` — существует один общий прогресс, который входит только в совместный отчёт.

Совместная запись применяется к цели один раз независимо от того, кто нажал кнопку. Поле `recorded_by` показывает автора действия, но не меняет владельца результата.

### 5.4. Права на записи и аудит

- Личную запись может создать, изменить или удалить только владелец личной цели.
- Запись по совместной цели может создать или исправить любой из двух участников;
  удалить её нельзя, результат остаётся одним общим.
- В аудите каждой записи сохраняются первоначальный `recorded_by`, последний редактор, время изменения, причина исправления, а также прежнее и новое состояние или значение.
- «Отменить последнее действие» в месяце выбранной записи отменяет только
  последнее ещё не отменённое собственное действие пользователя. Если оно
  относится к другой записи или результат после него изменён партнёром либо
  системой, более старое действие не выбирается. Повторная отмена идёт назад
  по собственному стеку; создание становится отсутствием факта, исправление
  возвращает прежнее значение, а удаление личной записи восстанавливает её.
- Другой интерфейс показывает изменение после следующего обновления страницы, повторного открытия экрана или явного обновления данных. Не обещается неопределённое «мгновенное» обновление.

## 6. Основные понятия

| Понятие | Определение |
| --- | --- |
| Каталог целей | Постоянный список переиспользуемых целей. Удаление из интерфейса архивирует цель, но не стирает историю. |
| Линия цели | Стабильная аналитическая идентичность одной и той же цели между месяцами. |
| Месячный план | Набор снимков целей для конкретного календарного месяца. |
| Снимок цели | Неизменяемая после публикации конфигурация цели внутри месяца. |
| Фиксированная цель | Цель с конкретным ожидаемым днём, датой или контрольной точкой. |
| Гибкая цель | Цель с нормой `N` за неделю или месяц без заранее закреплённых дней. |
| Запись | Факт, значение, оценка, текст или статус, внесённый пользователем. |
| progressPercent | Фактический процент прогресса цели; может быть больше 100%. |
| goalScore | Нормализованная оценка цели для агрегирования: для негибкой цели — `min(progressPercent, 100%)`, для гибкой — результат с отдельным ограничением каждого недельного или месячного периода по правилам §12.4. |
| monthScore | Среднее `goalScore` оцениваемых целей одного отчётного разреза. |
| Coverage | Полнота заполнения ожидаемых фиксированных записей или checkpoints. |
| Успешный применимый личный день | День, когда владелец либо явно закрыл день, либо заполнил каждое причитающееся ему фиксированное ожидание. |

## 7. Жизненный цикл месячного плана

### 7.1. Состояния

Месячный план проходит состояния:

1. `draft` — состав и настройки можно менять;
2. `published` — конфигурация зафиксирована, доступны ежедневные записи;
3. `grace` — месяц закончился, но записи ещё можно исправлять;
4. `closed` — записи и отчёт зафиксированы.

### 7.2. Создание и перенос

- Первый черновик создаётся из одноразового стартового шаблона по `monthly-plan-template`.
- При выборе стартового шаблона вошедший участник явно указывает, кем он является
  в исходнике — Участник А или Участник Б; второй участник получает оставшуюся persona.
  Эта привязка сохраняется вместе с использованием шаблона, не создаёт разных
  ролей или прав и не выводится из технического membership slot.
- Следующий месяц можно создать пустым или скопировать из выбранного прошлого месяца.
- У месячного плана есть обязательное текстовое поле «фокус месяца»: оно редактируется только в `draft`, входит в неизменяемый снимок после публикации и переносится при копировании как часть конфигурации.
- При копировании переносятся конфигурации снимков целей, ссылки на линии целей и порядок целей, но не записи, статусы, заметки и результаты.
- Копирование не меняет исходный месяц.
- В пространстве может быть не более одного опубликованного плана на календарный месяц.

### 7.3. Публикация, активация и блокировка

- Публикация требует preview и явного подтверждения.
- Preview привязан к exact draft revision, local activation date и deterministic hash; он показывает фокус, ordered goals, owners, весь typed config/provenance, рассчитанный calendar и все blockers, но не меняет план.
- Подтверждение передаёт только exact preview schema/hash versions и hash вместе
  с draft revision; activation, target month, goals, owners, config и formula
  versions сервер заново выводит из locked draft. Изменение любого из этих
  значений либо local date отклоняет старое подтверждение и предлагает заново
  открыть preview.
- Публиковать разрешено только план текущего или следующего календарного месяца по `Asia/Yekaterinburg`; неопубликованный план прошедшего месяца публиковать нельзя.
- План следующего месяца публикуется как зафиксированная будущая конфигурация и активируется ровно в `00:00` первого дня своего месяца. До этого момента записи и уведомления по нему недоступны.
- План текущего месяца активируется при публикации; правила поздней публикации применяются с даты публикации.
- План нельзя опубликовать, если в нём остались неоднозначные нормы, некорректные единицы, незаполненные обязательные поля или несовместимые настройки целей.
- До начала месяца опубликованный план можно вернуть в `draft`, только если в нём ещё нет записей.
- После начала месяца состав, типы, владельцы, нормы и расписания опубликованного плана не меняются.
- Изменение или архивирование каталожной цели влияет только на черновики и будущие месяцы.
- Успешная публикация атомарно фиксирует один неизменяемый snapshot: focus,
  ordered goal metadata/config/provenance, exact calendars, prorated targets,
  formula versions и подтверждённый preview hash. Частично опубликованного
  месяца, второго активного snapshot или публикации без command receipt/audit
  не существует.
- Тот же command ID с тем же подтверждением безопасно возвращает созданную
  publication revision. Другой command ID после уже состоявшейся публикации
  открывает существующий published plan, а не создаёт вторую revision.

### 7.4. Поздняя публикация

Если план опубликован после первого числа:

- датой начала становится дата публикации по `Asia/Yekaterinburg`;
- предыдущие дни получают системный статус `not_applicable`;
- эти дни не входят в `progressPercent`, `goalScore` или coverage;
- недельные и месячные нормы пропорционально уменьшаются;
- уведомления за прошлые дни не создаются.

`not_applicable` не является физической пользовательской записью. Fixed dates и
полностью preactivation weekly planned task, которые P04 исключил, остаются
отсутствующими expectations/periods; UI и отчёт выводят N/A из неизменяемой
activation/repetition metadata. Quota weeks/month сохраняются полностью,
включая preactivation periods с target `0`.

### 7.5. Закрытие месяца

- В `00:00` первого дня следующего месяца план переходит в `grace`.
- Grace period длится три полных календарных дня.
- В `00:00` четвёртого дня следующего месяца план автоматически переходит в `closed`.
- В `grace` отчёт помечается как предварительный и пересчитывается после каждой исправленной записи.
- Закрытый месяц можно открыть повторно только с обязательной текстовой причиной.
- Повторное открытие переводит план обратно в `grace` с маркером «повторно открыт» и разрешает исправлять записи, но не конфигурацию плана.
- Аудит хранит автора, время, причину, старое и новое значение.
- После повторного закрытия отчёт получает пометку «пересмотрен».
- Уведомления завершённого месяца при повторном открытии не возобновляются.

## 8. Каталог и линия цели

### 8.1. Поля каталожной цели

Каталог хранит определения в состояниях `active` и `archived`. Создание
определения создаёт первую неизменяемую версию и новую аналитическую линию;
последующие подтверждённые версии не переписывают предыдущие. Копирование
создаёт новое active-определение с собственной первой версией и новой линией,
не меняя источник. Архивирование и восстановление меняют только состояние
определения и никогда не удаляют определения, версии или линии. Одинаковые
названия разрешены.

На этапе versioned catalog каждая версия хранит ровно:

- название;
- отдельное пояснение или мотивацию `why`;
- категорию;

Эти строки обязательны, не могут состоять только из пробельных символов,
сохраняются без trim/Unicode normalization и ограничены Unicode code points:
название `1..200`, `why` `1..2 000`, категория `1..100`. Повторное сохранение
тех же metadata как нового подтверждённого изменения создаёт следующую версию.

Typed-конфигурация цели добавляется в редакторе черновика и содержит:

- владельца;
- тип измерения;
- правило повторения;
- цель и единицу измерения, если применимо;
- режим количества `targeted` или `informational`, если тип — количество;
- агрегацию значений `add` или `latest`, если тип — количество;
- агрегацию checkpoints `independent` или `all`, если checkpoints есть;
- точность числа: 0–3 знака после запятой;
- контрольные точки и сроки, если применимо;
- варианты выполнения, если применимо;
- порядок отображения;
- ссылки на каталожное определение, его версию и аналитическую линию.

Metadata-only catalog version сама по себе не может быть добавлена в черновик
или опубликована до создания typed-конфигурации.

### 8.2. Сохранение аналитической линии

Линия цели сохраняется при изменении в будущем черновике:

- названия или пояснения;
- категории;
- числовой нормы;
- частоты;
- порядка отображения.

Catalog API требует явного решения `continue` или `new` для каждой новой
metadata-версии и не пытается вывести его автоматически. На этапе typed
редактора продукт принудительно выбирает новую линию при изменении следующих
семантических осей.

Линия сохраняется при любом изменении частоты или модели повторения — `daily`, выбранные weekdays, `N/week`, `N/month` или one-off, — если не изменились смысл, владелец, тип, единица, агрегация, варианты и checkpoints.

Новая линия создаётся при изменении:

- типа измерения;
- владельца;
- единицы или точности;
- режима агрегации `add/latest`;
- состава checkpoints или их агрегации `independent/all`;
- состава вариантов «или»;
- смысла цели, даже если название похоже.

Сравнение месяцев для одной линии выполняется по нормализованному проценту, поэтому изменение нормы не разрывает историю.

### 8.3. Exact P03 draft contract

Редактор сохраняет structurally valid, но ещё неполный `DraftGoalConfigV1` и
отдельно вычисляет publishable `GoalConfigV1`. Не выбранный owner, nullable
required leaf или пустой required collection сохраняются и возвращаются как
value-free blocker `required|empty_collection|incompatible`. Неверный
discriminator/type, extra field, non-canonical UUID/date/time/decimal,
duplicate/forged child ID или превышение bound отклоняет весь запрос с `422` и
zero writes. Blockers возвращаются все сразу в стабильном порядке и не являются
HTTP Problem.

Publish validator является единственной обычной точкой создания refined
`GoalConfigV1`: он возвращает либо publishable config без blockers, либо null
config и непустой blocker list. Compile-time opaque marker не сериализуется;
следующие расчёты не могут принять непроверенный draft обычным вызовом API.

Exact repetitions: `daily`; unique canonical Monday-order weekdays;
`weekly|monthly` с canonical positive integer string `N`; `one_off` с canonical
date; `weekly_planned_task` с ordinal `1..5` и configured task text. В P03
one-off проверяется только на синтаксис и completeness; принадлежность месяцу и
calendar eligibility определяет P04. Weekly planned task использует boolean
measurement для week-level `done/not_done`: его configured task text является
описанием плана, а не ежедневным text fact; personal и shared scope разрешены,
daily checkpoint запрещён.

Exact measurements: boolean; targeted/informational quantity с unit, precision
`0..3`, `add|latest` и canonical nonnegative decimal target; actual-time
`HH:mm` range с overnight и различными endpoints; safe-integer rating с
`minimum < maximum`; text; ordered checklist; ordered OR variants с собственным
label/unit/precision/positive target. Informational quantity имеет null target;
targeted и quantity child/variant complete только с positive target; quantity
checkpoint использует precision parent quantity measurement. Checklist,
OR и checkpoint arrays содержат не более 100 элементов; один draft и reorder
payload — не более 200 active goals. Required text/unit/name/label до 500
Unicode code points, non-whitespace.

Checkpoints разрешены только для daily, имеют `independent|all`, stable UUID,
name, `HH:mm` deadline и satisfaction discriminator того же measurement kind.
Quantity и actual-time checkpoint задают собственный target/range; checklist и
OR используют parent composition. Parent и child arrays не нормализуются;
server создаёт ID для новых children, update сохраняет существующие и отвергает
forged/duplicate/cross-component reuse.

Optional provenance имеет exact `{ schemaVersion: 1, sourceDocument,
sourcePage, rawValue, rawDenominator, resolution }`: required document/
resolution non-whitespace до 500 code points, positive safe page, nullable raw
fields до 2,000. Оно сохраняется byte-for-byte, меняет idempotency fingerprint,
но не series identity, formulas или score.

В draft одновременно существует не более одного active attachment одной
definition; повторный add отклоняется finite `422` без записи. Удаление только
tombstones attachment; повторное добавление этой
definition создаёт новый plan-goal, config revision и child IDs. Draft-copy
operation в P03 нет: catalog definition копирует P02, затем её добавляет P03;
перенос месячного черновика остаётся P09.

Порядок active draft goals всегда плотный `0..count-1`, максимум 200 строк.
History remove/reorder сохраняет полные exact before/after ID arrays: reorder —
перестановку одного active set, remove — тот же set без удалённого goal. При
этом typed event обязан ссылаться на current/adjacent config revisions, exact
parent draft transition и completed receipt того же plan month/revision;
ложный previous order либо unrelated aggregate не коммитится. При
смене source catalog version её catalog series заменяет effective series только
если она отличается от catalog series предыдущей source version. Обычная
`continue` version не сбрасывает уже созданную typed effective series; hard
typed-axis change создаёт новую series, compatible update сохраняет текущую.

## 9. Типы целей

### 9.1. Выполнено / не выполнено

- Одно применимое ожидание принимает `done`, `not_done` или остаётся без данных.
- Для цели «не чаще одного раза в день» повторная отметка обновляет существующую запись, а не создаёт второе выполнение.

### 9.2. Количество

- У цели есть произвольная единица: например `мл`, `шаги`, `страницы`, `минуты`, `руб.`, `подписчики`.
- `add` суммирует отдельные порции: `400 мл + 800 мл = 1200 мл`.
- `latest` хранит последнее актуальное значение: `2000`, затем `7000 шагов = 7000`, а не `9000`.
- Отрицательные значения запрещены, если цель явно не поддерживает их в будущей версии.
- `targeted` требует точную числовую цель и участвует в напоминаниях, `progressPercent`, `goalScore` и `monthScore`.
- `informational` обязательно содержит единицу и агрегацию, но не имеет целевого значения, напоминаний, `progressPercent`, `goalScore` или вклада в `monthScore`; его факты и графики сохраняются.
- Если у количественной строки источника нет цели, черновик требует явного выбора `targeted` с введённой целью либо `informational`; молчаливое назначение запрещено.
- Значение выше целевой нормы сохраняется полностью; `progressPercent` показывает перевыполнение, а `goalScore` ограничен 100%.

### 9.3. Фактическое время

- Пользователь выбирает дату ожидания и вводит фактическое локальное время.
- Цель задаётся диапазоном начала и окончания.
- Диапазон может пересекать полночь, например `22:30–07:00`.
- Для диапазона через полночь часть после `00:00` относится к выбранной предшествующей дате ожидания: при выборе ожидания 10 апреля ввод `07:00` засчитывается ему, а не создаёт ожидание 11 апреля.
- Попадание в диапазон влияет на `goalScore`; любое корректное введённое время учитывается в coverage и графике.

### 9.4. Оценка по шкале

- Настраиваются минимальное и максимальное значение шкалы.
- Можно создать несколько именованных контрольных точек: например «утро», «день», «вечер».
- Низкое настроение не считается невыполнением цели.
- `goalScore` этого типа отражает заполнение обязательных контрольных точек, а сами значения используются только в трендах и наблюдениях.

### 9.5. Текстовая запись

- Для каждого применимого дня или checkpoint пользователь вводит непустой текст.
- Запись дополнительно получает результат `done` или `not_done`.
- Это позволяет вести «важную задачу дня», адресатов для коллабораций и другие данные, возникающие после публикации плана.
- Непустой текст считается заполнением для coverage; только `done` даёт выполнение в `goalScore`.

### 9.6. Разовая задача и чек-лист

- Разовая задача имеет дату выполнения и статус.
- Чек-лист содержит именованные подпункты.
- `progressPercent` чек-листа равен доле выполненных подпунктов; `goalScore` ограничен 100%.
- Частично выполненный чек-лист не считается полностью закрытой целью.
- Для разового или фиксированного чек-листа каждый обязательный подпункт — отдельное фиксированное ожидание для coverage; родитель не создаёт дополнительную единицу.

### 9.7. Варианты выполнения «или»

- Одно повторение может иметь несколько способов выполнения со своими единицами и порогами.
- Пример: `100 страниц` или `60 минут аудио`.
- Прогресс повторения равен максимальной нормализованной доле одного варианта.
- Значения разных вариантов не складываются между собой.
- Достижение 100% любого варианта закрывает повторение.

### 9.8. Универсальные checkpoints

- Любая ежедневная цель может содержать несколько именованных контрольных точек.
- У checkpoint есть название, порядок и срок в течение дня.
- У такой цели обязательно задан `checkpointAggregation`: `independent` или `all`; отдельного дополнительного ожидания у родительской цели нет.
- Каждый checkpoint наследует тип измерения родительской цели. При `independent` каждый child имеет отдельные факты, статусы, coverage и детальный процент, а его обязательный target задан явно; родитель имеет один `progressPercent` и `goalScore`, равные среднему процентов применимых children, и учитывается в `monthScore` один раз.
- При `all` у каждого child есть собственное явно заданное правило удовлетворения; один родительский день является единицей `goalScore` и coverage и считается `done` только когда удовлетворены все обязательные children. Значения детей сохраняются отдельно.
- Режим питания использует `all`: завтрак до `09:30`, обед `11:30–12:30`, ужин `18:30–20:00`. Настроение использует `independent` для утреннего, дневного и вечернего checkpoints.

## 10. Правила повторения

Поддерживаются:

- каждый день;
- выбранные дни недели;
- ровно `N` раз за календарную неделю;
- ровно `N` раз за календарный месяц;
- один раз к конкретной дате.
- `weekly_planned_task` — задача с configured text, заданная в черновике на
  календарную неделю без фиксированного дня; её measurement — boolean, и она
  получает `done` или `not_done` только на уровне недели. Configured text не
  является ежедневным text fact.

Для гибких недельных и месячных целей `N` — целое число `>= 1`. Диапазоны вроде «2–3 раза» не являются допустимой опубликованной нормой: пользователь должен выбрать одно точное значение `N` в черновике.

Календарная неделя идёт с понедельника по воскресенье, но статистический долг не переносится через границу месяца.

## 11. Статусы записей и закрытие дня

Для ожидаемой фиксированной записи различаются:

- `done` — выполнено;
- `not_done` — явно не выполнено;
- `no_data` — ожидаемая запись отсутствует;
- `not_applicable` — запись системно не требовалась.

`no_data` является вычисляемым состоянием отсутствия записи, а не отдельной пользовательской кнопкой.

### Закрытие дня

- Действие «Закрыть день» показывает все незаполненные фиксированные пункты и checkpoints выбранной текущей или прошедшей применимой даты.
- После подтверждения они становятся `not_done` одной операцией.
- Уже заполненные и будущие пункты не меняются.
- Закрытие прошедшей даты доступно до автоматического закрытия месяца, включая первые три дня обычного `grace`; после correction deadline незакрытый день остаётся `no_data` и автоматически не превращается в `not_done`.
- Участник закрывает свои personal и shared-ожидания; personal-ожидания партнёра остаются read-only.
- Для гибких недельных и месячных целей пропуск предложенного дня не создаёт `not_done`.
- Промежуточное отставание гибкой цели от равномерного темпа — только сигнал для экрана и напоминаний, а не `not_done`.
- `not_done` гибкой цели определяется только как дефицит при закрытии соответствующей недели или месяца.
- `weekly_planned_task` не включается в «Закрыть день»: в течение своей
  активной календарной недели owner выставляет week-level `done/not_done`, а
  исправление выполняется с причиной по общим правилам correction window.
  Если пользовательского результата нет, автоматическое закрытие недели
  относится к отдельному системному сценарию CloseWeek.

Пример: за 30 применимых дней цель выполнена 18 раз, 6 раз явно не выполнена и 6 раз не заполнена. `progressPercent` и `goalScore` равны `18 / 30 = 60%`, coverage — `(18 + 6) / 30 = 80%`.

## 12. Расчёты

Во всех формулах `round_half_up` означает обычное арифметическое округление половины вверх.

### 12.0. Calendar eligibility

Все календарные расчёты пилота используют локальные даты
`Asia/Yekaterinburg`, переданные явно, и proleptic Gregorian calendar с годами
`0001..9999`. Дата активации обязана находиться в target month. Правила
повторения применяются так:

- daily ожидается на каждой дате от activation включительно; weekdays — только
  на выбранных weekdays от activation. One-off due date валидна внутри target
  month: она создаёт expectation только при `dueDate >= activation`, иначе
  означает `not_applicable`; due date вне target month блокирует публикацию.
- weekly и monthly имеют active и eligible dates от activation включительно.
  Month — один период. Week — календарная Monday–Sunday week, пересечённая с
  target month: первая и последняя недели могут быть partial, но знаменатель
  weekly proration остаётся `7`. Все недели месяца сохраняются, включая
  pre-activation weeks с target `0`; deficit/surplus между ними не переносится.
- weekly planned task выбирает одну month-bounded calendar week по ordinal
  `1..5`; leading partial week имеет ordinal `1`. В месяце с шестью segments
  ordinal `5` выбирает пятый, шестой не получает задачу. Отсутствующий ordinal
  в четырёхсегментном месяце блокирует публикацию. Выбранная полностью
  pre-activation week означает `not_applicable`; activation внутри выбранной
  week сохраняет одну цель на эту week с исходными clipped bounds. Это одна
  week-level цель с target `1`, без daily expectations и равномерного daily
  pace.

Calendar incompatibility возвращается как безопасные blocker data, а не
подменяется ближайшей датой/неделей. Calendar-target behavior имеет version
`planner.calendar-targets.v1`; изменение перечисленных правил создаёт новую
версию и не переписывает закрытые отчёты.

### 12.1. Неполная неделя

Для гибкой цели `N` раз в неделю:

```text
если activeDays = 0:
  periodTarget = 0
иначе:
  periodTarget = min(
    max(1, round_half_up(N × activeDays / periodDays)),
    eligibleDays
  )
```

Где:

- `periodDays = 7`; `activeDays` — число дат пересечения календарной недели с активной частью месяца: от даты активации включительно до конца месяца включительно; у опубликованного заранее плана активная часть начинается в `00:00` первого дня месяца;
- `eligibleDays` — активные допустимые даты этого периода для цели; гибкое повторение засчитывается максимум один раз за такую дату.

Примеры для `N = 3`:

- пять активных дней: `round_half_up(3 × 5 / 7) = 2`;
- три активных дня: `round_half_up(3 × 3 / 7) = 1`.

### 12.2. Поздний старт месячной цели

```text
если activeDays = 0:
  periodTarget = 0
иначе:
  periodTarget = min(
    max(1, round_half_up(N × activeDays / periodDays)),
    eligibleDays
  )
```

Здесь `periodDays = daysInMonth`, `activeDays` — число активных дат месяца, а `eligibleDays` — активные допустимые даты месяца. Например, при `N = 10`, 30-дневном месяце и публикации 15-го числа `activeDays = 16`, поэтому цель месяца равна `round_half_up(10 × 16 / 30) = 5`.

### 12.3. Равномерный темп

Для гибкого периода:

```text
expectedProgress = round_half_up(
  periodTarget × elapsedEligibleDays / totalEligibleDays
)
```

- Текущий день включается в `elapsedEligibleDays`.
- Цель считается актуальной на сегодня, если фактический прогресс ниже `expectedProgress`.
- После каждой новой или исправленной записи расчёт выполняется заново.
- После достижения `periodTarget` напоминания до следующего периода прекращаются.
- Неиспользованный долг не переносится в следующую неделю или месяц.

### 12.4. progressPercent и goalScore цели

- Фиксированная boolean-цель: `progressPercent = 100% × done / applicableExpectations`.
- Целевое количество: `progressPercent = 100% × actual / target`; при нескольких применимых ожиданиях используется среднее их процентов. Информационное количество не имеет этих показателей.
- Составная гибкая цель считает на каждой допустимой дате `occurrenceProgress` в диапазоне `[0, 1]`: boolean, time и text дают `1` только при `done`, иначе `0`; quantity — `min(actual / target, 1)`; checklist — `completed / total`; «или» — максимум нормализованных долей вариантов, ограниченный `1`.
- `actualEquivalentOccurrences` равно сумме `occurrenceProgress` по допустимым датам периода; это и есть `actualProgress` гибкой цели для темпа и уведомлений. Для `N/week` каждая календарная неделя считается отдельно: `credited = min(actualEquivalentOccurrences, periodTarget)`; для `N/month` применяется тот же расчёт к одному месячному периоду.
- Для гибкой цели за отчётный месяц `progressPercent = 100% × sum(actualEquivalentOccurrences) / sum(periodTarget)`, а `goalScore = 100% × sum(credited) / sum(periodTarget)`. Для `N/month` обе суммы содержат один месячный период. Лишнее выполнение одной недели не закрывает дефицит другой: оно видно в сырых фактах и `progressPercent`, но не увеличивает `credited` этой недели.
- Time-range: `progressPercent = 100% × valuesInsideTargetRange / applicableExpectations`.
- Rating с `independent`: у каждого child свой детальный процент `100% × filled / applicable`, а родительский `progressPercent` — среднее процентов применимых children; с `all`: `progressPercent = 100% × daysWithAllRequiredChildrenSatisfied / applicableParentDays`.
- Text: `progressPercent = 100% × doneEntries / applicableExpectations`.
- Checklist: `progressPercent = 100% × completedItems / totalItems`.
- Вариант «или»: `progressPercent` повторения — максимальный процент одного варианта; варианты не складываются.
- Для не-гибких оцениваемых целей `goalScore = min(progressPercent, 100%)`; для гибких используется сумма `credited` по правилам выше. Если у цели нет применимых ожиданий, оба показателя равны `N/A`.

Незаполненное, но применимое ожидание даёт 0 в `progressPercent`; `not_applicable` исключается из знаменателя.

### 12.5. monthScore

```text
monthScore = average(goalScore for each scored goal)
```

- Каждая оцениваемая цель имеет одинаковый вес.
- Личные и совместные цели агрегируются в разных отчётах.
- Если оцениваемых целей нет, результат равен `N/A`.
- `progressPercent` показывает перевыполнение, но оно не увеличивает `goalScore` и `monthScore` выше 100%.

Пример: цели `100%`, `50%` и `130%` дают `(100 + 50 + 100) / 3 = 83,33%`.

### 12.6. Coverage и личная полнота дней

```text
coverage = filledFixedExpectations / applicableFixedExpectations
```

К заполненным относятся `done`, `not_done` и корректное измерение. `no_data` остаётся в знаменателе, но не в числителе. `not_applicable` не входит ни в один из них. Для `all` весь родительский день считается заполненным только при заполнении всех обязательных children; для `independent` считаются отдельные children. У разового или фиксированного checklist каждый обязательный подпункт считается отдельно: `done`, `not_done` или корректно заполненный статус входят в числитель, `no_data` — только в знаменатель, `not_applicable` исключается; родитель не добавляет ещё одну единицу. Гибкие квоты не входят в coverage и оцениваются отдельно по итоговому прогрессу периода.

Личная coverage и личный порог 80% используют только личные цели соответствующего владельца. Совместная coverage рассчитывается отдельным разделом и не входит в личные 80%. Применимый личный день содержит хотя бы одно причитающееся владельцу фиксированное ожидание; он успешен, когда владелец закрыл день либо заполнил все такие ожидания. Личный показатель полноты дней: `successfulApplicableDays / applicablePersonalDays`.

### 12.7. Exact evaluation, as-of и версии формул

Goal evaluation имеет version `planner.goal-evaluation.v1`, а агрегирование
monthScore/coverage — независимую version `planner.score-coverage.v1`. Каждый
результат цели также сохраняет exact calendar provenance
`planner.calendar-targets.v1`; изменение одной формулы не переименовывает две
другие и не переписывает закрытые отчёты.

Вычисление получает exact `CalendarTargetsInput` рядом с successful P04
calendar. Pure evaluator повторно применяет P04 policy и требует полного
structural совпадения результатов: forged, truncated или inconsistent calendar
не может изменить denominator/target, а ineligible provenance не оценивается.
P05 не копирует календарные формулы и не принимает один только unchecked
successful DTO.

Все проценты вычисляются как exact nonnegative rational. Внешнее отображение
имеет integer basis points: `100% = 10000`, `83,33% = 8333`,
`130% = 13000`. `round_half_up` применяется ровно один раз к итоговой метрике,
а не к children, occurrences или целям перед агрегированием. Поэтому среднее
`1/2` и `1/6` равно `33,33%`, не `33,34%`. Decimal facts и targets не
преобразуются через binary floating-point. Для защиты pure synchronous
boundary действует deterministic exact-work budget: до `250000` canonical
numeric input digits, `10000` exact terms, `250000` projected output digits,
`25000000` multiplication и `50000000` divmod digit-work units. Это не
per-field decimal limit и не timeout: допустимый результат всегда exact, а
превышение до дорогой allocation возвращает typed `input_too_complex` без
approximation. Один equality-fast-path ratio с `100000` digits остаётся
допустим. Raw digit lengths начисляются до сокращения даже для equal ratio;
единый `10000`-term ledger отклоняет oversized top-level/nested arrays до
обхода keys/descriptors и allocation. Каждый принятый rational полностью
сокращён bounded string arithmetic независимо от длины либо rejected тем же
deterministic budget.

Расчёт принимает явную локальную дату `asOf`:

- fixed expectation входит начиная со своей даты; будущая expectation не
  считается `no_data`;
- quota или weekly planned task period входит целиком, когда наступил его
  `periodStart`, но facts после `asOf` не учитываются;
- до первой применимой единицы показатели равны `N/A`, после месяца участвует
  весь month calendar;
- `not_applicable` определяется только опубликованным календарём и `asOf`, а не
  пользовательским фактом.

Facts являются текущим authoritative state. Для `add` суммируются active
projection-wide unique contributions с opaque domain `contributionId` (не ID
строки БД/revision), для `latest` берётся одно текущее значение. Отсутствие fact —
`no_data`; explicit `not_done` заполнен для fixed coverage, но даёт нулевое
достижение. Время сравнивается с inclusive endpoints; overnight value попадает
при `value >= start` или `value <= end`. Любой valid rating, включая minimum,
является заполнением и достижением: magnitude не означает успех или провал.

Для independent checkpoints raw progress равен exact mean raw child ratios, а
goalScore — exact mean child ratios после отдельного cap `100%` каждого child.
Перевыполнение одного child не компенсирует другой; разность остаётся отдельным
overperformance. Checklist child даёт coverage unit на каждый item, остальные
children — по одной unit на дату. Для `all` одна parent-date unit выполнена
только при удовлетворении всех children и заполнена только при полном
заполнении всех children. Any-of считается заполненным при хотя бы одном
variant value либо explicit `not_done`; его progress остаётся максимумом, не
суммой.

Для flexible quota occurrence ratio ограничен `[0,1]`. Каждый наступивший
period отдельно вычисляет actual equivalent, credited capped его target и
overperformance. Итоги делят суммы на сумму targets наступивших ненулевых
periods; surplus одной недели не переносится. Flexible quota, включая
informational quantity, не входит в coverage. Fixed informational quantity
остаётся coverage unit при valid measurement, но не получает progress/score.

`weekly_planned_task` после начала своей недели является одной scored
week-level boolean unit: `done = 100%`, `not_done/no_data = 0%`. Она не входит
в fixed/day coverage и не добавляет coverage denominator.

Goal result хранит uncapped progress, capped score, separate overperformance,
exact ratios, basis points и fixed coverage counts. Агрегатор принимает цели
одного уже выбранного personal/shared раздела: monthScore — exact равновесное
среднее доступных goalScore, coverage — отношение сумм filled/applicable.
Informational и `N/A` score исключаются; нулевой score denominator даёт
`N/A`, как и нулевой fixed coverage denominator. Пример `100/50/130` считается
как exact `(100 + 50 + 100) / 3 = 83,33%`; coverage `1/1` и `0/9` равна
`1/10 = 10%`, а не среднему `50%`.

### 12.8. Publication preview

Preview пересчитывает P03 validation и P04 calendar для каждой
publishable цели. Текущий month активируется на сегодня, а
следующий — на первое число. Иной month всё равно даёт
revision-bound preview с blocker на `targetMonth`, чтобы UI мог показать
точную причину. Empty goals сами по себе не блокируют
публикацию.

Расчёт не имеет facts и не синтезирует progress, score, coverage или
`no_data`; versions P05 передаются как явная compatibility
metadata. Два участника пространства получают одинаковый actor-free
preview и hash. Hash включает всё показанное и рассчитанное состояние,
включая revisions, activation, provenance, blockers и formula versions. Любая
значимая правка draft или смена local date изменяет hash; повтор
без изменений byte-stable.

### 12.9. Publication snapshot

Публикация повторно строит ровно тот же preview после locked read и сохраняет
confirmed preview hash как publication snapshot hash; отдельного P07 hash
algorithm нет. Generated publication/snapshot IDs и timestamps в hash preimage
не добавляются. Published snapshot возвращает exact source revisions, focus,
ordered goal snapshots, copied metadata/refined config/provenance, successful
P04 calendars/targets и calendar/evaluation/score formula versions. Он остаётся
byte-stable после последующих изменений draft или каталога.

Fixed calendars materialize coverage components так: scalar/`any_of` без
checkpoints — одно parent expectation на дату; checklist без checkpoints — по
одному item expectation без дополнительного parent; при checkpoints — по
одному checkpoint expectation, а его nested checklist/any-of остаётся будущим
checkpoint fact. Weekly/monthly quota и weekly planned task materialize periods,
не daily expectations.

Одна publication materialize не более `10 000` строк суммарно: goal snapshots,
expanded fixed expectations и flexible periods. Ровно `10 000` допустимы.
Превышение добавляет до preview hash один plan-level blocker
`{planGoalId:null,pointer:'/goals',code:'incompatible',detail:'Publication
materialization exceeds 10000 rows.'}`; preview остаётся deterministic и
доступным как `200`, а подтверждение exact blocked preview не создаёт
publication, child rows, history или receipt.

Все preview blockers входят в hash в deterministic порядке: plan-level перед
goal-level; goal-level по display order и goal ID; одинаковая plan/goal позиция
по pointer, code и detail, включая несколько blockers с null `planGoalId`.

## 13. Веб-интерфейс

Веб должен быть адаптивным и содержать:

1. **Сегодня** — план дня, быстрый ввод, прогресс и закрытие дня.
2. **Месяц** — календарь и состояния по датам.
3. **Каталог** — создание, копирование, архивирование и восстановление целей.
4. **Черновик** — состав, порядок, владельцы, нормы, checkpoints и проверка ошибок.
5. **Публикация** — preview, список блокирующих конфликтов и подтверждение.
6. **Статистика** — личные и совместные отчёты и графики.
7. **Настройки** — времена уведомлений, состояние Telegram identity и доступа бота, управление пространством.

Запись допускается исправлять с аудитом до автоматического закрытия месяца, включая `grace`; после автоматического закрытия — только после повторного открытия с причиной. При одновременных несовместимых правках продукт сохраняет уже подтверждённую запись и предлагает пользователю обновить экран и повторить действие. Другие интерфейсы увидят изменение при следующем обновлении или открытии экрана.

Полный web pilot зависит от backend-owned HTTP/read-model capabilities,
которых нет в OpenAPI baseline `44f00d0`. Требования `GAP-01…GAP-09`, их
security/recovery semantics и отдельная граница доказательств зафиксированы в
[Frontend API Addendum](./FRONTEND_API_ADDENDUM.md). До merge соответствующих
tasks frontend не хардкодит persona/member UUID, не вызывает application layer
напрямую и не имитирует отсутствующие commands набором частичных mutations.

## 14. Telegram

### 14.1. Личные чаты

- Каждый пользователь работает в личном чате бота.
- Основное меню: «Сегодня», «Месяц», «План», «Статистика», «Настройки».
- Личные уведомления не отправляются партнёру.
- Выполнение общей цели синхронно исчезает из актуальных действий у обоих.

### 14.2. Пилот

В пилоте доступны:

- вход через Telegram OIDC и проверка доступа в личном чате бота;
- просмотр «Сегодня»;
- ввод каждого ежедневного типа: boolean, целевого и информационного количества, фактического времени, оценки, текста, чек-листа, варианта «или» и каждого checkpoint;
- исправление или удаление собственной личной ошибочной записи; любой участник может исправить совместную запись с обязательной причиной;
- отмена последнего действия;
- закрытие дня;
- просмотр текущего прогресса;
- уведомления.

Создание и настройка плана в пилоте выполняются в вебе.

### 14.3. Завершённая v1

Через Telegram дополнительно доступны:

- создание и копирование черновика;
- добавление, настройка, сортировка и архивирование цели;
- устранение блокирующих ошибок;
- preview и публикация;
- настройка уведомлений;
- просмотр итоговой статистики.

Свободный текст используется только в конкретном ожидаемом шаге мастера: название, число, время, заметка или причина.

### 14.4. Мастера

- Состояние мастера сохраняется 24 часа.
- Доступны Back, Cancel и Resume.
- До финального подтверждения продуктовые данные не меняются.
- Перед подтверждением показывается полный preview.
- Устаревшая кнопка безопасно открывает актуальное состояние.
- Если веб изменил данные во время мастера, бот сообщает о конфликте и предлагает обновить данные с повтором текущего шага.

### 14.5. Идемпотентность

- Веб и Telegram используют один набор продуктовых команд и правил валидации.
- Повтор одной операции возвращает прежний результат.
- Повторная отправка действия не создаёт второй факт, второй вклад `add` или вторую отметку boolean/checkpoint в том же ожидании.
- Если данные на экране устарели, продукт не перезаписывает уже подтверждённый результат: он показывает актуальное состояние и предлагает повторить выбор.

## 15. Уведомления

### 15.1. Настройки

- У каждого пользователя свои утреннее, дневное и вечернее время.
- Каждый слот можно отключить.
- Все времена интерпретируются в `Asia/Yekaterinburg`.
- Один слот отправляется максимум один раз по ключу `user + localDate + slot`.

### 15.2. Утро

Сообщение содержит:

- обязательный фокус месяца;
- обязательные фиксированные пункты на день;
- гибкие цели, которые отстают от равномерного темпа;
- текущий прогресс без уже закрытых норм.

### 15.3. День

Сообщение содержит:

- незаполненные checkpoints, срок которых уже наступил;
- незакрытые фиксированные пункты со сроком не позднее текущего слота;
- гибкие цели, которые всё ещё ниже планового темпа.

### 15.4. Вечер

Сообщение содержит:

- все оставшиеся применимые фиксированные пункты и checkpoints;
- гибкие цели текущего периода только когда `actualProgress < expectedProgress`;
- действие «Закрыть день».

### 15.5. Подавление и сбои

- Разрешённая дневная запись перестаёт упоминаться после `done`, `not_done` или корректного измерения; для целевого количества подавление наступает после достижения нормы.
- Выполненная недельная или месячная норма не упоминается до следующего периода.
- Совместная гибкая цель следует общей slot relevance: пока она ниже темпа, единый shared progress виден обоим и одна частичная отметка не может скрыть цель только у её автора; после достижения общей нормы цель исчезает у обоих.
- Для частичного количества показывается остаток до нормы.
- Если актуальных пунктов нет, сообщение не отправляется.
- Фокус месяца не создаёт самостоятельное утреннее сообщение: он включается только в уже актуальное сообщение.
- Просроченное сообщение не доставляется после наступления следующего слота или следующего дня.
- После восстановления сервиса накопленные старые уведомления не отправляются пачкой.
- Если пользователь заблокировал бота или бот больше не может отправлять ему сообщения, веб показывает предупреждение.

## 16. Статистика и графики

### 16.1. Разрезы

Отчёт содержит три независимых раздела:

- Участник Б;
- Участник А;
- совместные цели.

Совместные цели не увеличивают личный `monthScore` обоих участников.

### 16.2. Пилотный отчёт

- `monthScore`, `goalScore` и отдельно `progressPercent` по каждой оцениваемой цели;
- coverage;
- `факт / цель` и процент по каждой цели;
- календарная heatmap с различием `done`, `not_done`, `no_data` и `not_applicable`;
- накопительные графики количественных целей;
- тренды фактического времени;
- тренды оценок.

### 16.3. Расширенная аналитика v1

- текущая и лучшая серия;
- распределение результатов по дням недели;
- распределение по категориям;
- фактический и требуемый темп;
- прогноз итога;
- сравнение с закрытыми прошлыми месяцами по линии цели.

### 16.4. Серии

- Для ежедневной цели серия — последовательность применимых дней с достигнутой нормой.
- Для выбранных дней недели учитываются только выбранные дни.
- Для гибкой недельной цели серия — последовательность недель с достигнутой, в том числе пропорционально уменьшенной, нормой.
- `not_done` и `no_data` обрывают фиксированную серию.
- `not_applicable` пропускается и не обрывает серию.

### 16.5. Прогноз

Прогноз появляется после трёх активных дней периода только для целевого количества и гибких целей:

```text
projectedResult = actualProgress / elapsedEligibleDays × totalEligibleDays
```

Для целевого количества `actualProgress` — накопленный факт в единице цели, `target` — целевое количество периода; для гибкой цели `actualProgress` — число выполнений, `target = periodTarget`. `elapsedEligibleDays` — уже прошедшие допустимые дни, `totalEligibleDays` — все допустимые дни периода. Статус «успеваем» показывается, если `projectedResult >= target`. Прогноз является простой экстраполяцией, не использует ML и не подменяет фактический результат.

### 16.6. Корреляционные наблюдения

- Наблюдение использует коэффициент ранговой корреляции Спирмена и доступно только при наличии не менее 90 парных значений двух выбранных показателей на одну и ту же локальную дату.
- Пропущенные значения не подставляются; в расчёт входят только даты с обоими фактическими значениями. Показываются коэффициент и число парных наблюдений, а также предупреждение об отсутствии причинного вывода.
- Формулировка допускает только описание: «в наблюдаемых днях показатели менялись совместно».
- Медицинские советы и формулировки «X вызывает Y» запрещены.

## 17. Будущая ИИ-фаза

Пользователь сможет написать: «Сегодня прошёл 2000 шагов и выпил 400 мл воды».

ИИ должен:

1. сопоставить фрагменты с опубликованными целями;
2. сформировать пакет предлагаемых структурированных записей;
3. показать цель, дату, значение, единицу и способ агрегации;
4. запросить подтверждение или исправление;
5. сохранить записи только после подтверждения.

ИИ является ещё одним адаптером общей системы команд и не пишет данные напрямую. Неоднозначный текст не сохраняется автоматически.

## 19. Стартовый шаблон

- `monthly-plan-template` используется только как источник одноразового шаблона и требований.
- Автоматический DOCX-импорт не разрабатывается.
- Фокус стартового месяца предзаполнен текстом «Показатель 108»; в `draft` его можно изменить.
- Каждая строка исходника должна быть сопоставлена с целью, checkpoint, подпунктом или вариантом «или».
- Пять строк outreach принадлежат Участник Б и переносятся как пять `weekly_planned_task`: их исходный текст и порядок копируются в черновик следующего месяца без назначения фиксированного дня.
- Комбинированные показатели при необходимости разделяются на несколько целей, например число коллабораций и доход.
- Показатель 088 `/50` — целевая месячная метрика `targeted`; новые подписчики MAX без target и доход от коллабораций — информационные метрики `informational` с единицами соответственно `подписчики` и `руб.`, явной агрегацией, без нормы и напоминаний, но с фактами и графиками.
- В стартовом шаблоне медитации имеют точную месячную норму `N=16`; бумажный итог `/20` сохраняется только как происхождение исходных данных.
- Обе исходные нормы `2–3 раза в неделю` получают точное значение `N=2`: для фитнес-клуба или домашней тренировки Участник Б и для совместной активности.
- Перечисленные каналы Reels и постов/статей используют режим `all`: каждое повторение требует выполнения всех перечисленных каналов соответствующей цели.
- Показатель 075 — целевая месячная метрика `targeted` с `N=7` и агрегацией `add`; доход от коллабораций остаётся отдельной информационной метрикой.
- «Одна важная задача дня» принадлежит `shared` и хранит один общий текст и результат на применимую дату.
- Бумажные итоговые знаменатели сохраняются как provenance для сверки. Недельные и дневные цели рассчитываются по календарным правилам продукта, включая неполные недели, позднюю публикацию и границы месяца; бумажный итог не переопределяет рассчитанный target.
- Эти значения являются заполненными данными стартового шаблона, а не константами продукта; в `draft` их можно изменить по общим правилам редактора.
- Стартовый черновик не публикуется автоматически.
- Стартовый шаблон можно применить ровно один раз на пространство к любому
  свободному canonical месяцу; повторное применение отклоняется, а exact replay
  возвращает первоначальный черновик revision `1`.

## 20. Сбои и защита данных

- Данные должны сохраняться между перезапусками и обновлениями сервиса.
- Каталожные цели и месяцы с историей не удаляются физически через обычный интерфейс.
- Повторные запросы веба, Telegram и будущего ИИ не создают дубли.
- При конкурирующих изменениях уже подтверждённый результат сохраняется, а пользователь получает актуальное состояние и возможность повторить своё действие.
- Неуспешное уведомление не влияет на возможность заполнить план в вебе.
- Отсутствие опубликованного плана отключает ежедневные уведомления и показывает обоим участникам понятное действие для создания или публикации черновика.
- События публикации, открытия закрытого месяца и изменения записей входят в аудит.
- До пилотного запуска должен успешно пройти практический drill восстановления из резервной копии; политика резервного копирования, RPO и RTO остаются решениями технического дизайна.

## 21. Приёмочные сценарии

### AC-01. Пространство пары

**Дано:** числовые Telegram user ID Участник Б и Участник А внесены в закрытый allowlist, а в пространстве есть их личные цели и одна совместная цель.  
**Когда:** каждый участник завершает Telegram OIDC Authorization Code flow с PKCE и открывает план в локальной веб-сессии.  
**Тогда:** проверенные `issuer + subject` и Telegram user ID связываются с правильным локальным участником; оба видят весь план и имеют равные права, личные результаты попадают только владельцу, а совместный результат учитывается один раз в отдельном разделе.

### AC-01b. Закрытый OIDC fail-closed

**Дано:** вход выполняется через Telegram OIDC.  
**Когда:** не проходит проверка `state`, `nonce`, PKCE, подписи/claims либо numeric Telegram user ID отсутствует в allowlist.  
**Тогда:** новый пользователь и локальная сессия не создаются, данные пространства не открываются; scope `phone` не запрашивается, а изменение username не меняет существующий mapping `(issuer, subject) + Telegram user ID`.

### AC-02. Перенос месяца

**Дано:** опубликованный апрельский план содержит настройки и записи.  
**Когда:** создаётся черновик мая на основе апреля.  
**Тогда:** настройки и линии целей копируются, записи не копируются, а изменение мая не меняет апрель.

### AC-03. Блокировка публикации

**Дано:** у гибкой недельной цели не задано точное целое `N`, а у количества в режиме `targeted` отсутствует target.  
**Когда:** пользователь пытается опубликовать план.  
**Тогда:** публикация отклоняется с отдельной ошибкой у каждого незаполненного или некорректного поля.
**Когда:** после preview изменились draft revision, focus/config/order/
provenance, catalog metadata, local activation date, formula/calendar либо
появился новый blocker.
**Тогда:** старое подтверждение отклоняется; publication, snapshots,
expectations, periods, month pointer/revision, history и receipt не изменяются.

### AC-04. Неполная неделя

**Дано:** цель равна трём выполнениям в неделю.  
**Когда:** в первой неделе месяца пять активных дней.  
**Тогда:** норма равна двум.  
**Когда:** в последней неделе три активных дня.  
**Тогда:** норма равна одному, а результат прошлого месяца не переносится.

### AC-05. Поздняя публикация

**Дано:** в 30-дневном месяце цель равна `N = 10`, а план опубликован 15-го числа.  
**Когда:** рассчитываются ожидания и цели.  
**Тогда:** дни 1–14 выводятся как `not_applicable` без физических fixed rows,
прошлые уведомления отсутствуют, quota calendar сохраняет preactivation period
с target `0`, а цель месяца равна `5`.

### AC-06. Количество `add/latest`

**Дано:** вода использует `add`, шаги используют `latest`.  
**Когда:** введены `400` и `800` мл, а также `2000` и затем `7000` шагов.  
**Тогда:** вода равна `1200` мл, шаги — `7000`; повтор callback не меняет
результаты. Независимые `add` сохраняются как отдельные contributions, а
Boolean/`latest` обновляются только с актуальной fact revision; одна успешная
команда увеличивает `factsRevision` месяца ровно один раз.

### AC-07. Время, rating и checkpoints

**Дано:** время сна имеет диапазон через полночь, а настроение — три checkpoints.  
**Когда:** после полуночи фактическое время явно записано на expectation date
предыдущего дня, утро и день заполнены значениями minimum/maximum, вечер
пропущен.
**Тогда:** time-range выполнен; значения настроения не интерпретируются как успех или провал; вечер остаётся `no_data` до закрытия дня.

### AC-08. Варианты «или»

**Дано:** повторение закрывается 100 страницами или 60 минутами аудио.  
**Когда:** пользователь вводит 50 страниц и 30 минут.  
**Тогда:** прогресс повторения равен 50%, а не 100%, потому что варианты не складываются.  
**Когда:** один вариант достигает своего порога.  
**Тогда:** повторение закрывается.

### AC-09. Закрытие дня

**Дано:** часть фиксированных пунктов выполнена, часть явно не выполнена, часть не заполнена, а гибкая недельная цель отстаёт от темпа.  
**Когда:** пользователь закрывает день.  
**Тогда:** только незаполненные фиксированные пункты становятся `not_done`; гибкая цель не получает дневного провала.

### AC-10. Подавление уведомлений

**Дано:** личная недельная норма выполнена, а применимая общая норма совместной цели достигнута.  
**Когда:** наступает следующий слот уведомлений.  
**Тогда:** личная цель не приходит её владельцу, а достигнутая общая норма не приходит обоим; до достижения нормы shared-цель ниже темпа имеет одинаковую relevance для обоих, а при отсутствии других актуальных пунктов сообщение не отправляется.

### AC-11. Grace period и аудит

**Дано:** месяц находится в `grace`.  
**Когда:** запись исправлена до `00:00` четвёртого дня.  
**Тогда:** отчёт пересчитывается.  
**Когда:** то же действие выполняется после закрытия.  
**Тогда:** оно отклоняется до подтверждённого повторного открытия с причиной и аудитом.  
**Когда:** месяц повторно открыт с причиной и запись исправлена.  
**Тогда:** аудит сохраняет автора, причину и изменение; конфигурация плана остаётся заблокированной, отчёт пересчитывается, а уведомления завершённого месяца не возобновляются.

### AC-12. Конфликт веба и Telegram

**Дано:** Telegram-мастер открыт на старой версии черновика, которую уже изменили в вебе.  
**Когда:** пользователь подтверждает мастер.  
**Тогда:** изменение не применяется поверх новой версии; бот предлагает обновить данные и повторить текущий шаг.

### AC-13. Итоговый monthScore

**Дано:** три цели имеют результаты `100%`, `50%` и `130%`.  
**Когда:** рассчитывается общий итог.  
**Тогда:** `progressPercent` третьей цели равен `130%`, её `goalScore` равен `100%`, а `monthScore` равен `83,33%`.

### AC-14. Полнота данных

**Дано:** у ежедневной цели 30 применимых дней: 18 `done`, 6 `not_done`, 6 `no_data`.  
**Когда:** строится отчёт.  
**Тогда:** `progressPercent` и `goalScore` равны `60%`, coverage — `80%`, а heatmap визуально различает все состояния.

### AC-15. Корреляционные наблюдения

**Дано:** для пары показателей есть менее 90 парных значений.  
**Тогда:** наблюдение не показывается.  
**Дано:** доступно не менее 90 парных значений.  
**Тогда:** показываются коэффициент Спирмена, размер выборки и предупреждение; пары собраны на одни и те же даты без подстановки пропусков, причинный или медицинский вывод отсутствует.

### AC-16. Целевая дата времени

**Дано:** ожидание сна относится к 10 апреля и имеет диапазон `22:30–07:00`.  
**Когда:** пользователь вводит для ожидания 10 апреля фактическое время `07:00` после полуночи.  
**Тогда:** ввод засчитывается 10 апреля, а не 11 апреля.

### AC-17. Shared correction

**Дано:** Участник Б внесла частичное значение совместной цели.  
**Когда:** Участник А исправляет его с причиной до автоматического закрытия месяца.  
**Тогда:** в аудите сохранены первоначальный автор, Участник А как редактор и причина; если общий progress остаётся ниже темпа, shared-цель видна обоим, а после достижения общей нормы уведомления прекращаются у обоих.

### AC-18. Составная гибкая цель

**Дано:** у гибкой цели `N=2` за неделю две допустимые даты с выполнением по `50%`.  
**Когда:** рассчитывается неделя.  
**Тогда:** `actualEquivalentOccurrences = 1`, `credited = 1`, а `goalScore` периода равен `50%`.  
**Когда:** в этой же неделе добавляются ещё два полных выполнения, поэтому `actualEquivalentOccurrences = 3`, а в другой неделе остаётся дефицит.  
**Тогда:** `credited` первой недели ограничен значением `2`, её `goalScore` равен `100%`, и лишнее эквивалентное выполнение не компенсирует дефицит другой недели.

### AC-19. Coverage чек-листа

**Дано:** у фиксированного чек-листа четыре обязательных подпункта: два `done`, один `not_done`, один `no_data`.  
**Когда:** строится отчёт.  
**Тогда:** `progressPercent` и `goalScore` равны `50%`, coverage равен `75%`, а родительский checklist не добавляет отдельное ожидание.

### AC-20. Текстовая запись

**Дано:** у ежедневной текстовой цели есть применимое ожидание.  
**Когда:** пользователь сохраняет непустой текст с `done` или `not_done`.  
**Тогда:** запись считается заполненной для coverage; только `done` увеличивает `goalScore`, а пустой текст не сохраняется.

### AC-21. Информационное количество

**Дано:** новые подписчики MAX и доход от коллабораций настроены как `informational`.  
**Когда:** пользователь вводит корректные факты.  
**Тогда:** факты и графики обновляются, но у целей нет target, напоминаний, `goalScore` и вклада в `monthScore`.

### AC-22. Каналы исходного плана

**Дано:** стартовый черновик содержит Reels для «вк», «Дзен», «тик-ток», «инст» и пост/статью для Показатель 024.  
**Когда:** пользователь открывает preview публикации.  
**Тогда:** обе цели представлены checklist-целями в режиме `all`, все перечисленные каналы являются обязательными подпунктами одного повторения, а бумажные `/8` показаны только как provenance.

### AC-23. Weekly planned task

**Дано:** в исходнике есть пять outreach-строк по календарным неделям.  
**Когда:** создаётся следующий черновик.  
**Тогда:** пять `weekly_planned_task` переносятся с исходным текстом и порядком, без фиксированного дня и без создания ежедневных ожиданий.

### AC-24. Закрытие weekly planned task

**Дано:** у владельца есть `weekly_planned_task` текущей календарной недели.  
**Когда:** владелец в течение активной недели выставляет `done/not_done` либо
неделя заканчивается без результата.
**Тогда:** пользовательский week-level результат сохраняется отдельной
revisioned записью с автором и без daily expectations; повторный intent требует
correction с причиной. Незаполненная задача в `00:00` следующего понедельника
или на границе месяца становится `not_done` от system actor одной идемпотентной
CloseWeek-операцией, а «Закрыть день» её не изменяет.

CloseWeek обрабатывает одной группой все weekly planned tasks одной публикации
с одинаковыми календарными границами. Пользовательские `done/not_done` не
меняются; удалённый пользователем результат снова считается незаполненным и на
следующем worker tick получает новую системную revision `not_done` в новой
детерминированной closure generation. Источник текущей revision явно
показывается как участник либо `planner-worker`.

## 22. Проверка успеха пилота

Пилот признаётся успешным, если одновременно выполнены условия:

1. оба пользователя прошли allowlisted Telegram OIDC и получили локальные веб-сессии;
2. стартовый черновик проверен и опубликован;
3. весь календарный месяц ведётся без параллельной бумажной версии;
4. у каждого пользователя не менее 80% успешных применимых личных дней; совместные цели считаются отдельно;
5. повторные Telegram-действия не создали дублей;
6. достигнутые нормы перестали попадать в напоминания;
7. следующий месяц создан переносом без старых записей;
8. закрытый отчёт совпадает с исходными записями, статусами и формулами этого PRD.

### AC-SM-01. Целостность набора
